# Codex 잔량 표시 구현 계획

확인일: 2026-10-24. 3차 결과는 보존하고 4차에서 구현합니다. 사용자 요청은 기존 EXE에 실시간 Codex 토큰 잔량 표시를 추가하는 것입니다. 실제 제공 데이터는 남은 토큰 개수가 아닌 계정 사용 한도 비율입니다.

## 설계와 선택 근거

공식 `account/rateLimits/read`를 현재 PC에 설치된 `codex app-server`의 표준 입력·출력 연결로 조회합니다. [실제 계정 응답 수치 제외.] 남은 비율은 100-usedPercent입니다. 공개 문서: https://learn.chatgpt.com/docs/app-server . 이 read 요청만 허용하며 새 작업·모델 추론·로그인·리셋·구매·사용자 설정 변경 요청을 보내지 않습니다.

검토한 대안은 로컬 세션의 과거 사용량을 읽는 방식과 채팅 도구 결과를 정기 파일로 전달하는 방식입니다. 전자는 사용 중이지 않으면 갱신되지 않고, 후자는 채팅 실행에 종속되어 독립 EXE 배포에 부적합합니다. 현재 확인된 공식 조회를 Qt 비동기로 연결하는 방식을 부모가 선택합니다. 앞서 설명에 머물지 말고 직접 구현하라는 사용자 지시에 따라 추가 설계 승인 질문은 생략합니다.

## 구현 범위

- 새 `src/usage.py`: 설치된 Codex EXE 탐색, 숨김 QProcess 연결, initialize/initialized/read 순서, 물리적 LF JSON 파싱·응답 크기 상한·응답 시간 제한, 30초 자동 갱신·업데이트 수신·수동 조회, 제한된 재연결, 정상 종료와 본인이 시작한 프로세스 정리.
- `src/app.py`: 투명 회전 위젯의 작은 잔량 표시와 상세 창의 계정 사용 한도 패널·초기화 시각·조회시각·새로고침 버튼. 기존 다크테크·나눔고딕 Bold700 유지. API 키·로그인·복잡한 서버 설정을 제품 흐름에 노출하지 않습니다. 자동 탐색 실패 시 Codex EXE 선택 안내를 제공합니다.
- `tests/test_usage.py` 및 기존 앱 검사: 실제 응답 형태, 5시간/주간/다중 버킷, null/누락/비정상 값, JSON 부분 조각·과다 응답, 인증/실행실패/연결 종료·타임아웃·중복조회·종료, UI 표시·낡은 수치 구분. 테스트를 먼저 실패시키고 구현 후 통과를 확인합니다.
- `assets/사용법.md`, `README.md`: 잔량 단위·30초 주기·수동 갱신·실패 표시·설치된 Codex 로그인 필요를 안내합니다. 인증 파일과 사용자 대화·사용량을 배포에 넣지 않습니다.

## 성공 조건과 검증 순서

1. 실제 설치된 Codex에서 새 잔량을 조회하고 위젯 및 상세 창에 표시합니다. 기간은 duration으로 판별하며 없는 5시간 한도를 만들어 넣지 않습니다. null을 0% 또는 100%로 만들지 않습니다. 초기화 시간이 지났다고 서버 재조회 전 잔량을 임의 복구하지 않습니다.
2. UI는 조회 중에도 회전·드래그·MD·모델 알림을 유지합니다. 실패 시 과거 값은 지연/이전 조회로 명시하거나 미확인으로 표시하며 현재 값으로 가장하지 않습니다. 다른 계정의 값이 디스크 캐시에서 섞이지 않도록 사용량을 영구 복원하지 않습니다.
3. 테스트·엄격 UTF-8·구문 검사 후 단일 EXE와 설치본 재빌드, 격리 경로에서 실행/설치/실행/제거 및 MD 보존을 확인합니다.
4. 구현자와 다른 verifier Sol/high가 실제 로그·사용량 조회·UI·실패 경로·배포를 직접 대조합니다. 소스 동결과 실제 로컬 child 실행 근거를 부모가 등록하고 독립 verifier만 검증 영수증을 발급합니다.

기술 스택은 기존 Python3.12/PySide6/Qt/QProcess/PyInstaller/Inno를 사용합니다. parent는 빌드·설치 도구와 증거·라우팅·계획을, 구현자는 usage/app/tests/사용 안내를 소유합니다. 상호 변경을 되돌리지 않습니다. 동시 설치 검사는 하지 않습니다.

## 추가 사용자 요구와 알림 진단

사용자가 같은 작업 중 모델 변경마다 알림이 나오지 않는다고 보고했습니다. 실제 기존 앱 프로세스가 떠 있어도 C 앱 데이터 heartbeat/state/history는 17:32에 멈췄습니다. state 복사본에서 4회 poll0.625초로 실제 새 배정 3건을 읽었으며, 이전 앱을 정상 종료하고 같은 데이터 경로를 명시해 재실행하자 18:48에 heartbeat와 이력이 다시 갱신됐습니다. 이전 프로세스 정지의 최초 원인은 미확정이며 재실행 성공을 원인 수리로 가장하지 않습니다.

별도 기존3차 Qt 격리 재현에서 first/second/third 연속 이벤트는 이력3건이나 말풍선은 third로 덮어써졌습니다. 이 확정된 표시 결함은 FIFO 대기 후 닫기·클릭·만료 시 다음 알림을 표시하고 대기 수를 안내하는 방식으로 수리합니다. 과부하 상한과 이력 안내로 조용한 유실을 피합니다. 감시 상태는 마지막 진행 신호가 오래됐으면 지연으로 명시하고, 실제 종료된 작업자만 제한된 재시작을 합니다. 살아 있는 정체 스레드를 기다려 UI를 막거나 강제 종료하지 않습니다. 연속3건·재표시·클릭 정확ID·수동유지·종료·지연 검사를 추가합니다.
